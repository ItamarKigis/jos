=== Q Compare kern/mpentry.S side by side with boot/boot.S. Bearing in
===   mind that kern/mpentry.S is compiled and linked to run above KERNBASE
===   just like everything else in the kernel, what is the purpose of macro
===   MPBOOTPHYS? Why is it necessary in kern/mpentry.S but not in
===   boot/boot.S? In other words, what could go wrong if it were
===   omitted in kern/mpentry.S?
===   (free form)
	The purpose of MPBOOTPHYS is to calculate the absolute addresses of its symbols(labels, etc.) when we want to refer to them.
	It is necessary in kern/mpentry.S because the secondary cpu starts to run in MPENTRY_PADDR, but the linker might place the code it in a different virtual 	address,  so we correct it by this macro no matter where the linker placed the code.

	But in boot.S, the code is linked directly to the right address space, so we don't need adjustments. Because there is a fixed address where the bootloader
	will always be loaded: 0x7C00, the linker will always load the code there.

=== Q It seems that using the big kernel lock guarantees that only one
===   CPU can run the kernel code at a time. Why do we still need
===   separate kernel stacks for each CPU? Describe a scenario in
===   which using a shared kernel stack will go wrong, even with the
===   protection of the big kernel lock.
===   (free form)
	Because the CPU modifies the kernel stack immediately with parameters when receiving an interrupt, even before trying to acquire the lock.
	For example, one program generates a page fault, it's cpu pushes the trap frame to the stack and then acquire the lock.
	In this time, second program divides by zero, thus it's cpu also pushes the trap frame to the kernel stack, overwriting the previous trap frame in the page fault case, and then it proceeds to 	wait on the big kernel lock but the intervention has already happened.

    First we implemented a syscall called sys_batch that takes an array of 4

    sys_batch loops over the enum array and calls syscall() on each element
